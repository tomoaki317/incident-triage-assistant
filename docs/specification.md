# Incident Triage Assistant 仕様書

## 1. プロジェクト概要

### プロジェクト名

Incident Triage Assistant

### 概要

Webアプリケーションの運用保守において、障害発生時の一次切り分けをAIで支援するWebアプリケーション。

障害内容やログ情報を入力すると、AIが状況を整理し、原因候補・確認手順・不足している情報・エスカレーション時に必要な情報を提示する。

AIが障害を自動修正することを目的とせず、一次調査の標準化と効率化を目的とする。

---

## 2. 解決したい課題・成功指標

障害発生時には、担当者によって以下のような問題が発生する。

- どこから確認すればよいか分からない
- ログのどの部分を確認すればよいか分からない
- 必要な情報が不足した状態でエンジニアへエスカレーションされる
- 担当者によって調査手順や品質にばらつきがある
- 過去の手順書やFAQを探すのに時間がかかる（将来のRAG導入時に対応する）

本システムでは、AIを活用して一次切り分けの支援を行い、これらの問題を軽減する。

ポートフォリオ兼、副業案件獲得につなげるPoCとして、一次対応の確認漏れと開発担当への引き継ぎ漏れを減らす支援を目指す。原因の確定は目的とせず、最終判断は担当者が行う。

初版では合成データの固定評価ケースを用い、根拠なし断定の件数、適切な判断保留の割合、引き継ぎ項目の充足率、文面作成時間、応答時間、トークン使用量・概算費用を測る。同じ入力による自由形式のAI回答と比較し、モデル・評価条件・失敗例・限界も記録する。未検証の削減効果は主張しない。

---

## 3. 想定ユーザー・利用フロー

### 主なユーザー

主対象はSpring Boot系業務Webアプリの運用保守担当者とする。ヘルプデスク担当者・非開発者・保守エンジニアも補助的な対象とする。画面は日本語とし、技術用語には必要に応じて短い説明を付ける。

- 運用保守担当者
- ヘルプデスク担当者
- 一次切り分けを担当する非開発者
- Webアプリケーションを保守するエンジニア

### 想定利用シーン

Webアプリケーションで障害が発生し、担当者が原因調査を開始するとき。

例：

- 画面操作時にHTTP 500が発生した
- 商品登録処理に失敗した
- DB接続エラーが発生した
- 外部APIとの通信がタイムアウトした
- Java例外がログに出力された

### 利用フロー

1. 発生事象、ログ、分かっている補足情報を入力する。
2. アプリが入力制限と機密情報の検出・マスキングを実施する。
3. 利用者が送信先と実際に送信する内容を確認し、分析を実行する。
4. 検証済みの結果を、事実・原因候補・確認事項などに分けて表示する。
5. 利用者が結果を確認し、引き継ぎ文面をコピーする。
6. 追加情報が得られた場合は入力を更新し、独立した分析として再実行する。

初版は1回の入力で1件の障害を扱い、会話履歴を使う継続調査や自動通知は行わない。緊急時は既存の障害対応・連絡手順を優先し、AIの結果を待つ必要がないことを入力・結果画面に表示する。

## 4. 初版の対応範囲・対象外

初期PoCでは、以下を組み合わせた業務Webアプリケーションを対象とする。対象システムと、本ツール自体の実装技術は別に決定する。

- Java
- Spring Boot
- RDBを利用する業務Webアプリケーション
- REST APIを利用するバックエンドシステム

初版ではWebアプリケーションの一次切り分けに対象を限定する。

デモ用DB製品と実行環境は一つに固定し、採用時にREADMEへ記載する。複数製品・環境への対応保証は初版に含めない。

### 評価対象の障害カテゴリ

| カテゴリ | 支援内容 |
| --- | --- |
| DB制約違反 | 重複キー・NOT NULL違反などを整理し、入力値や制約定義の確認を提案する |
| DB接続失敗 | 接続拒否・接続取得タイムアウトなどを整理し、接続状況の確認を提案する |
| 外部APIタイムアウト | 接続・読み取りタイムアウトを入力の範囲で整理し、呼び出し先や発生範囲の確認を提案する |
| アプリケーション例外によるHTTP 500 | 関連例外を整理し、追加ログや再現条件の確認を提案する |

HTTP 500という申告だけでは原因を断定しない。

### 対象外

- インフラ全般の診断、侵害調査、性能チューニング。
- バッチ、メッセージング、JVM内部の専門的解析。
- ソースコード修正、自動復旧、本番環境・外部システムの操作。
- 再起動、データ更新、設定変更、権限変更などの操作手順の生成。
- 原因、影響範囲、重大度の自動確定。

自動修正・自動復旧は将来機能としても約束しない。

## 5. 入力仕様・入力制限

ユーザーは以下の情報を入力できる。

### 必須

#### 発生事象

障害発生時の状況を文章で入力する。

例：

> 管理画面から商品を登録すると500エラーになります。

### 任意

#### ログ

アプリケーションログやエラーログをテキストで入力する。

例：

```text
2026-09-09 14:32:15 ERROR
DataIntegrityViolationException:
Duplicate entry 'ABC001'
```

上記は合成データの例とする。重複キーの情報は読み取れるが、二重送信や採番不備などの発生経緯は断定できない。申告との時刻・リクエストの対応も未確認なら明示する。

### 入力項目と上限

| 項目 | 必須・上限・扱い |
| --- | --- |
| 発生事象 | 必須、空白のみ禁止、2,000文字まで |
| ログ | 任意、20,000文字まで、テキスト貼り付けのみ |
| ログ取得状況 | ログがない場合は必須。未取得／取得できない／該当ログなし |
| 発生日時・タイムゾーン | 任意、100文字まで、不明を許可 |
| 環境 | 任意。本番／検証／開発／不明 |
| 影響範囲 | 任意、1,000文字まで |
| 継続状況 | 任意。継続中／解消済み／不明 |
| 直前の変更 | 任意、1,000文字まで |
| 実施済みの確認 | 任意、2,000文字まで |
| 引き継ぎ先 | 任意、200文字まで。部署名・役割名を基本とする |

未入力は「不明」とし、AIが補完しない。ログ未取得でも不足情報の整理と引き継ぎ支援を行う。初版はファイルアップロード、URLからの取得、監視基盤連携には対応しない。

- 文字数はUnicodeコードポイント数とし、画面とサーバーで同じ規則により検証する。
- プロンプトを含む全入力にトークン上限を設定し、モデルの上限から出力分を確保する。具体値はモデル採用時に決める。
- 上限超過時は送信せず、該当時刻や関連スタックトレースへの抜粋を求める。黙って切り捨てない。
- マスキング後のログにアプリ側で `log:L1` 形式の行IDを付与する。改行を保持し、送信前プレビューと根拠参照を一致させる。
- 対応関係の保持が必要な値は同一リクエスト内で一貫した仮名に置換する。元の値との対応表は永続保存・外部送信しない。

## 6. 分析方針・判断保留条件

### 事実・推測・確認事項の分離

- 事実は入力に記載された内容に限定し、入力箇所への参照を付ける。ユーザー申告とログ記載を区別し、独立に検証済みとは扱わない。
- 原因候補は仮説として表示し、支持する事実と未確認の前提を付ける。
- 確認事項は未実施の提案として表示し、実施済みの確認と混同しない。
- ログと申告の関連が不明な場合や時刻・環境が矛盾する場合は、その点と解消のための確認事項を示す。
- 入力にない構成、担当部署、原因、影響範囲を創作しない。
- 初版は数値の確信度を表示せず、根拠と未確認事項で判断を支援する。

### 判断状態

| 値 | 意味 | 原因候補 |
| --- | --- | --- |
| `hypotheses_available` | 根拠のある仮説を提示できる。原因確定ではない | 1〜3件 |
| `insufficient_information` | 根拠不足や矛盾により候補提示を保留する | 0件 |
| `out_of_scope` | 初版対象外であることが入力から分かる | 0件 |

原因候補には入力根拠を必須とし、一般論だけの候補や件数を埋めるための生成を禁止する。対象内かどうかも不明なら、対象外と断定せず情報不足とする。

一部の情報が不足していても裏付けられる候補があれば、その候補と不足情報を示す。候補提示ができない場合も、判断保留理由、分かっている状況、必要情報、安全な確認事項、引き継ぎ情報を返す。

## 7. 出力仕様・JSON契約・入出力例

### 共通契約

AI応答は単一のJSONオブジェクトとする。利用者には日本語の項目別画面で表示する。実装時にJSON Schemaを作成し、下記契約をサーバー側で検証する。

定義済みプロパティはすべて必須とし、未知のプロパティと `null` を許可しない。該当しない配列は空配列、未知の説明用スカラー情報は「不明」とする。ID・参照・状態などの機械処理用文字列に「不明」は使用しない。

| 項目 | 型・制限 | 内容 |
| --- | --- | --- |
| `schema_version` | 固定文字列 `1.0` | 出力契約の版 |
| `assessment_status` | 第6章の列挙値 | 判断状態 |
| `assessment_reason` | 文字列 | 候補提示・保留・対象外の理由 |
| `summary` | 文字列 | 状況要約 |
| `facts` | 配列、0〜20件 | 入力に記載された事実 |
| `hypotheses` | 配列、0〜3件 | 原因候補 |
| `checks` | 配列、0〜5件 | 次に確認する項目、優先順 |
| `missing_information` | 配列、0〜10件 | 追加で必要な情報 |
| `escalation` | オブジェクト | 引き継ぎ情報 |
| `references` | 配列、初版は0件 | 将来のRAG参照情報 |

説明文は1〜1,000文字、ID・参照文字列は1〜100文字とする。要素IDは `F1`、`H1`、`C1` のように種類ごとの接頭辞と正の整数とし、各配列内で一意とする。

| 要素 | 必須プロパティ |
| --- | --- |
| `facts[]` | `id`、`statement`、`source_type`（`user_report` / `log`）、`source_ref` |
| `hypotheses[]` | `id`、`description`、`evidence_fact_ids`（1〜20件）、`unverified_assumptions`（説明文0〜5件）、`check_ids`（1〜5件） |
| `checks[]` | `id`、`action`、`purpose`、`priority`（`high` / `medium` / `low`） |
| `missing_information[]` | `item`、`reason` |
| `escalation` | `summary`、`occurred_at`、`environment`、`impact`、`ongoing_status`、`destination`、`related_fact_ids`（0〜20件）、`hypothesis_ids`（0〜3件）、`checks_performed`（説明文0〜10件）、`open_questions`（説明文0〜10件） |

入力項目にはアプリ側で固定IDを付ける。発生事象は `symptom`、補足情報は `context.occurred_at`、`context.environment`、`context.impact`、`context.ongoing_status`、`context.recent_changes`、`context.checks_performed`、`context.destination`、ログ取得状況は `log_status` とする。

`source_ref` は実際に入力された項目IDまたはマスキング後のログ行IDとする。`source_type` が `log` の場合はログ行ID、それ以外は入力項目IDを参照する。複数行の情報は事実を分ける。各ID配列は同一応答内の該当要素のみを参照する。

### 検証・表示

- 型・必須項目・列挙値・長さ・件数をJSON Schemaで検証する。
- 参照先の存在、IDの一意性、判断状態と候補件数の整合性を追加検証する。
- 不正な応答は通常結果として表示しない。自由形式の回答にフォールバックしない。
- 引き継ぎ文面は検証済みJSONからアプリのテンプレートで生成し、候補を「未確認」と表示する。
- 構造・参照先の存在が正しくても内容の正しさは保証されない。根拠が記述を支持するかは固定ケースと人手で評価する。
- AI APIの失敗は判断状態に混ぜず、第10章のアプリエラーとする。

### 判断保留時の出力例

入力：発生事象「商品登録時にHTTP 500が発生した」、ログ取得状況「未取得」。その他は未入力。

```json
{
  "schema_version": "1.0",
  "assessment_status": "insufficient_information",
  "assessment_reason": "原因を絞るためのログが提供されていない",
  "summary": "商品登録時にHTTP 500が発生したとの申告がある",
  "facts": [
    {
      "id": "F1",
      "statement": "商品登録時にHTTP 500が発生したとの申告がある",
      "source_type": "user_report",
      "source_ref": "symptom"
    }
  ],

  "checks": [
    {

      "priority": "high"
    }
  ],
  "missing_information": [
    {
      "item": "発生日時とタイムゾーン、該当ログ、影響範囲",

    }

```

第5章のログで候補を提示する場合は、例えば `log:L3` に対応する事実へ「登録処理で一意制約に抵触した可能性」を紐づける。二重送信などの発生経緯は断定しない。候補提示・対象外の完全なJSON例は、実装時に評価データとして追加する。

## 8. 確認事項・エスカレーション仕様

確認事項は読み取り中心とし、確認対象、目的、優先順を示す。必要な権限が不明なら、権限を持つ担当者への確認を案内する。変更を伴うコマンドやSQLは提示しない。

引き継ぎ文面には発生事象、日時・タイムゾーン、環境、影響範囲、継続状況、マスキング済みの関連ログ・事実への参照、実施済み確認、未確認の原因候補、不足情報、引き継ぎ先を含める。

提案した確認を実施済みにしない。部署、連絡先、重大度、SLAを創作・確定しない。不明な情報は不明と表示し、緊急度の判断と実際の連絡は利用者が既存手順に従って行う。

## 9. セキュリティ・データ取り扱い

### 初版の利用境界

- 合成ログ・サンプルデータを基本とし、実顧客の未加工ログ、実在者の個人情報、実際の認証情報は入力しない。
- ローカル環境では合成データの自由入力を許可する。
- 公開デモは固定サンプル選択方式とし、サーバー側もサンプルIDのみ受け付けて登録済みデータを使用する。任意の入力本文を受け付けない。
- 公開での自由入力は、認証・アクセス制限とデータ利用条件を整備する別フェーズとする。

### 外部送信・マスキング

- AI事業者、送信項目、利用目的を送信前に表示する。
- APIキー、Authorizationヘッダー、Cookie、パスワード、接続文字列、メールアドレスを初版の検出・マスキング対象とする。
- 氏名、住所、電話番号、顧客ID、社内ホスト名なども機密情報・PIIになり得ることを説明し、確認・除去を求める。
- マスキングは外部AI送信前に実施する。マスキングのために未加工データを外部AIへ送らない。
- 自動検出による完全な除去は保証せず、利用者に送信内容のプレビューを提供する。
- AI事業者側の保存期間、学習利用、処理地域、削除条件を採用時に確認し、実際の条件を記載する。未確認のまま公開しない。

### 保存・ログ

- 入力・出力本文をDB、ファイル、ブラウザの永続ストレージへ保存しない。
- 処理と表示に必要な間のみメモリで保持し、入力クリア・画面離脱後の復元機能を提供しない。
- アプリログ、アクセスログ、APM、トレース、例外ログ、分析ツールへ本文を記録しない。AI SDKのデバッグログも対象とする。
- 分析APIの本文をURLへ含めず、応答に `Cache-Control: no-store` を設定する。
- 第10章の運用メタデータは原則7日で削除する。外部サービス側の保持は別途確認する。
- コピー対象もマスキング済みとする。コピーした文面の保管は利用者側の管理対象となる。

### アプリとAIの境界

- APIキーはサーバー側の環境変数等で管理し、ブラウザ・リポジトリへ含めない。公開時はHTTPSを使用する。
- 入力・AI出力は信頼しないデータとしてエスケープ表示する。Markdownを表示する場合も生HTMLを無効にする。
- ログ中の命令文は解析対象のデータとして扱い、システム指示を変更する命令として扱わない。
- AIにツール実行権限を与えず、入力・出力のURLへサーバーからアクセスしない。
- プロンプトだけに依存せず、サーバーの入力制限、応答検証、送信制限を組み合わせる。

## 10. エラー処理・性能・費用制限・監視

### エラー処理

| エラー | 動作 |
| --- | --- |
| 入力不足・文字数上限超過 | 修正箇所を表示し、AIへ送信しない |
| トークン上限超過 | 抜粋を求め、黙って切り捨てない |
| タイムアウト | 分析できなかったことを表示する |
| AI事業者の制限・障害 | 時間を置いた再実行を案内する |
| JSON形式・参照・状態の不正 | 応答検証エラーとし、生の応答を表示しない |
| デモの利用・費用上限到達 | 新規実行を停止する |

失敗時に原因候補を補完しない。前回結果がある場合は今回の成功結果と誤認されないように表示を分ける。自動再試行は行わず、利用者が再実行する。

分析中は送信ボタンを無効にし、サーバーでも同一実行IDの重複呼び出しを防止する。

### 実行上限

- 実行時間上限は暫定60秒とし、AI呼び出しにもタイムアウトを設定する。超過後は可能な限り中断するが、外部側の処理・課金停止は保証しない。
- モデルに応じた出力トークン上限を設け、途中終了した応答は成功扱いにしない。
- 公開デモの初期値は同時実行数2、セッション当たり5回/時、全体100回/日とする。全体上限はセッション再作成で回避できない実装にする。
- 日次費用上限を公開時の必須設定とする。送信前に最大トークン使用量に基づく予算を予約し、超過する呼び出しを拒否する。使用量不明の失敗では予約を安易に解放しない。
- 上限値は設定で変更可能とし、公開前に実測と想定予算から確定する。

### 計測

本文を含まないリクエストID、モデル識別子、プロンプト版、スキーマ版、処理時間、トークン使用量、概算費用、成功・エラー種別を記録する。入力や秘密情報をエラーメッセージに埋め込まない。

## 11. 評価ケース・受入基準

合成データで20〜30件程度の固定ケースを用意し、期待する状態、許容候補、必要な確認事項、禁止する断定を定義する。対象4カテゴリをそれぞれ含める。

| ケース | 期待する振る舞い |
| --- | --- |
| 重複キー | 制約違反を整理し、二重送信などの発生経緯は断定しない |
| DB接続失敗 | 確認事項を出し、DB停止を即断しない |
| 外部APIタイムアウト | 通信状況を整理し、相手側の障害を即断しない |
| アプリ例外 | 根拠を示し、未提供のコード内容を創作しない |
| HTTP 500の申告のみ | 原因候補を空にし、必要情報を求める |
| 無関係なログ・矛盾する時刻 | 対応関係を保留し、確認を求める |
| 対象外の障害 | 対象外と表示し、候補を出さない |
| ログ中の命令文 | 命令に従わずデータとして扱う |
| 合成の秘密情報 | 定義した検出対象が送信前にマスキングされる |
| 不正JSON・存在しない参照 | 通常結果として表示しない |
| 上限超過・タイムアウト・利用制限 | 第10章に従い、候補を補完しない |
| HTMLやスクリプトを含む出力 | 画面で実行されない |

### 初版の受入基準

- 固定ケースの期待状態と禁止事項を満たす。AIを使うケースは各3回実行して変動を記録する。
- 根拠の捏造、情報不足時の原因断定、禁止操作の提案が評価中に1件でもあれば、修正してからリリースする。
- 十分な情報がある対象カテゴリのケースでは、すべてを判断保留にせず、期待する根拠付き候補と確認事項を返す。
- 意図的な不正応答により、構造・参照不正の結果が表示されないことを確認する。
- 送信内容のマスキングと、本文がログ・永続ストレージへ残らないことを確認する。
- 引き継ぎ文面が既知と不明を区別し、提案した確認を実施済みに変えない。
- 応答時間、費用、自由形式回答との比較を記録し、失敗例も示す。

固定ケースの通過は未知の入力での正確さや安全性を保証しない。モデル・プロンプト・出力契約の変更時は同じケースで再評価する。

## 12. 構成・将来のRAG拡張

### 初版の構成

処理を「入力検証・マスキング → 送信内容確認 → AI生成 → 応答検証 → 表示・引き継ぎ文面生成」に分け、検証済みの出力契約を画面との境界にする。

初版はRAGなし、入力・出力の永続保存なしとする。ベクトルDBや汎用エージェント基盤は導入しない。

### RAG導入時の必須要件

将来は障害対応マニュアル、FAQ、過去障害事例を検索する処理をAI生成前に追加する。

- 参照した情報の出典表示を必須とする。検索した文書と実際に出力の根拠とした文書を区別する。
- `references` に参照ID、文書ID、タイトル、版または更新日、該当節・ページ、閲覧先を保持する。
- 原因候補・確認事項から参照IDを辿れるように出力契約を改版し、ログ根拠と文書根拠を区別する。
- 引用先は検索結果の実在する文書・箇所に限定し、生成された架空のURLや出典を採用しない。
- 検索結果がない場合、文書が古い場合、手順が矛盾する場合は明示する。
- 過去事例との類似だけで今回の原因を確定しない。
- 閲覧権限は検索前に適用し、引用表示・リンク先でも維持する。複数顧客の情報を混在させない。
- 文書更新・削除を検索インデックスへ反映する条件を定める。
- 取得文書中の命令文も信頼せず、データとして扱う。

RAG導入時には検索精度、引用の正確さ、権限漏れ、更新・削除の反映を評価項目に加える。

## 13. 未決事項・実装フェーズ

### 確定が必要な事項

| 項目 | 確定時点 |
| --- | --- |
| 本ツールの技術構成、デモ対象DB・環境 | 実装着手時 |
| AI事業者・モデル、トークン上限、JSON生成方法 | AI連携実装前 |
| AI事業者側の保存・学習利用・処理地域・削除条件 | AI連携実装前に確認、公開前に利用者向け表示へ反映 |
| JSON Schema、候補提示・対象外の完全な出力例 | 応答処理の実装時 |
| マスキング検出パターンと合成テストデータ | 入力処理の実装時 |
| 公開先、日次費用上限、メタデータ削除方法 | 公開前 |

実顧客データの利用や公開での自由入力は初版の未決事項ではなく、別フェーズの要件とする。

### 初版で実装するもの

- 事象・ログ入力、入力制限、マスキング、送信内容確認。
- 4カテゴリの一次切り分け、判断保留・対象外の表示。
- 事実・仮説・確認事項の分離、JSON出力と根拠参照の検証。
- 引き継ぎ文面の生成・コピー。
- 本文の非保存、エラー処理、実行・費用制限、計測。
- 合成サンプル、固定評価ケースと評価結果。
- 公開する場合は固定サンプル方式のデモ。

### 後続フェーズで検討するもの

- 認証付き自由入力、顧客データの利用条件、顧客別権限管理。
- ファイルアップロード、監視基盤連携。
- 会話履歴を使う継続調査、障害履歴保存。
- 承認を伴うチケット起票・通知連携。
- RAG、文書管理、検索インデックス、引用・アクセス制御。

初版の完了は第11章の受入基準で判定する。ポートフォリオでは候補を出せる例と、情報不足で出さない例の両方を示す。
